Two Systems That Never Agreed on a Name

Principal Engineer Austin Sonny Stethem
Pricing & MDM Analyst 		Core Competencies Entity Resolution, Key Normalisation, Alias Governance, Non-Destructive Merge, Join Integrity Auditing Context Reconciling an 80-branch location master against a legacy transaction extract, and a 3,848-record location census across ten brand families.

1. The Failure That Doesn't Announce Itself

Where this sits Every model elsewhere in this portfolio: the elasticity tiers, the trade-area decay, the merger overlap, begins with a join between a transaction extract and a location master. This is the page about that join, and about what happens when it quietly fails.

A distribution network that has grown by acquisition, and that carried a mainframe-era system for decades, does not have one name for anything. The location directory calls a site by its division prefix and its facility role. The transaction extract calls it whatever a branch manager typed into a terminal in 1998. Both are correct inside their own system, and neither knows the other exists.

Joining them with an exact string match produced a file that looked complete. It was not. Ten of eighty branches — twelve and a half percent of the network — silently failed to match and were dropped from the analysis entirely. No exception was raised. No row count looked wrong, because the row count was never compared against anything. The tier model that followed was trained on a network with a hole in it.

The reason this class of bug is dangerous

A join that fails loudly costs an hour. A join that fails silently produces a smaller, cleaner-looking dataset and every downstream number is confidently wrong. An inner join is a filter wearing the costume of a lookup, and nothing in the output tells you it removed anything.

2. The Taxonomy of a Name Mismatch

The ten failures were not random noise. Sorted, they fall into six recognisable patterns; and knowing which pattern you are looking at determines which normalisation will fix it.

Pattern Location master Transaction extract Why it breaks, and what fixes it
Division prefix AMS Fairview Fairview The directory qualifies the site by operating division; the terminal never did. Fixed by stripping a known prefix set — not by fuzzy matching, which would also happily match a different town.
Facility suffix Northgate DC Northgate A role marker distinguishing a distribution centre from a retail branch, present in one system only. Fixed by a controlled suffix list.
Token transposition Riverton West West Riverton Identical tokens, opposite order. Edit distance scores this badly despite the strings being semantically identical: the case where a Levenshtein threshold tuned to catch typos will still miss. Fixed by comparing token sets instead of sequences.
Punctuation IPD-Sutton IPD Sutton One hyphen. An exact join fails on a single character that no human reader would notice. Fixed by normalising to alphanumerics and single spaces before comparison.
Opposing convention Orchard DC APW Orchard One system marks the facility with a suffix, the other with a division prefix. Requires both normalisations to run before either match succeeds — which is why the order of operations matters.
Genuinely absent Cylinder Works , A specialty operation with no matching transaction stream. The correct outcome is an explicit unresolved record, not a silent omission. A pipeline that cannot distinguish "no match" from "not attempted" cannot be audited.

3. Resolution, One Rule at a Time

The failed joins were on nobody's list, because a failed join does not surface as an error. It surfaces as a slightly smaller number. I found them by counting what the join dropped instead of trusting what it returned, and then owned the resolution rules instead of handing the problem to IT with a ticket attached.

The decision that shaped every rule below was which kind of error to prefer. Fuzzy matching at a loose threshold catches more pairs and occasionally fuses two real customers into a record belonging to neither — a wrong merge that a branch manager then has to unpick from live invoices. A strict rule misses pairs, and a miss is visible: the account simply does not appear. I chose narrow, curated rules over a similarity score for that reason. A rule that can only make one kind of mistake is one you can reason about; a threshold can make both and tells you which only in hindsight.

Enable the normalisation stages in order and watch the match rate climb. Each rule is deliberately narrow — a controlled list, not a similarity threshold; because a rule that can only make one kind of mistake is a rule you can reason about. Turn off the geospatial veto to see what a purely textual match does when two different places share a name.

4. What Production Actually Does

The dashboard above is the reasoning; the pipeline is the implementation. Six controls carry it, and each exists because a specific failure happened first.

A normalised key, computed before any join

Branch identifiers arrive in different shapes. One system carries an alphabetic prefix and zero-padding; the other carries neither. So both sides reduce to a canonical key before anything joins: prefix stripped, leading zeros removed, case folded. The join runs on the key. Never on the display name, because the display name is the thing that disagrees.

Alias sets, not similarity scores

The location census spans ten brand families, and brand identity does not map to a single string. A regional co-operative trades under its own name while operating another banner's stores. An acquired chain keeps old signage for years. A distributor runs several internal divisions that are one competitor for footprint purposes. Each family therefore has a multi-alias signature set, and membership is a lookup against curated aliases, not a distance calculation — because the relationship between a co-op's trading name and its banner is not a string-similarity fact. It is a fact about the industry.

An authoritative source per entity class

Records for our own branches are purged from the harvested census and re-injected from the internal directory. Scraped data is trusted for competitors and never for us. That is a governance decision, not a technical one: a scraper must not be permitted to become the system of record for entities the business already maintains authoritatively.

Merges that cannot destroy what they touch

When recovered records fold back into the master, a blank incoming value never overwrites a populated one. That is the commonest way a repair script does damage. A naive update writes nulls over good data and reports success. Deduplication follows the same rule: rows sort so populated records come first, and keeping the first occurrence keeps the useful one instead of an arbitrary one.

Disambiguation instead of deletion

Genuine near-duplicates — several operations at one physical address — are separated by a small coordinate offset so all of them remain visible and selectable on the map. The instinct to collapse coincident records is what erases real locations. Dedupe requires the name, the classification and the rounded coordinates to agree before anything is removed.

Bidirectional geocoding

Forward resolution turns an address into coordinates; reverse resolution turns coordinates back into an address for records that arrived with one and not the other. Running both directions closes the loop, and means an incomplete record can be repaired from whichever half of it survived.

5. The Question No Algorithm Answers

One of the ten failures is not a matching problem at all, and it is the one worth ending on.

Two separate master records — two operating divisions, physically co-located in the same town, both normalise to the same single name in the transaction extract. Every rule in the pipeline resolves them to the identical counterpart. The pipeline has not failed; it has correctly identified that the transaction stream does not distinguish between two businesses that the directory does.

No threshold setting resolves that. No library resolves it. Answering it requires knowing that one division sells parts over a counter and the other serves industrial accounts, that they share a lot, and which of them a given class of invoice belongs to. The correct engineering response is to stop, flag the record as ambiguous, and route it to somebody who knows the business — which is precisely why the dashboard reports an ambiguous count as a first-class outcome instead of folding it into a match rate.

What This Case Study Is Actually About

Not fuzzy matching. The algorithms are the easy part and they are all in libraries. The work is knowing that an inner join is a filter in disguise, that a transposed pair of words defeats edit distance while looking obvious to a human, that a co-op's trading name is a fact about the industry, not about strings, and that the honest output of a resolution pipeline includes a column for the records it could not resolve.

Every predictive model in this portfolio rests on this layer being right. A margin cascade computed across a network missing twelve percent of its branches produces confident, presentable, wrong numbers — and nothing in the output would tell you.

Where This Feeds

With identity reconciled, the transaction data can be attached to physical geography, which is the input the trade-area model and the competitive footprint both depend on.
